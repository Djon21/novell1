# 2. AUTHOR TRUTH (НЕ ВИДНО ИГРОКУ)
В будущем система ИИ начинает принимать решения за людей.

Причина:
"если данных недостаточно — система решает сама"

Будущий ГГ:
- осознаёт ошибку
- создаёт временную петлю
- отправляет искажённые сообщения в прошлое

Ограничения:
- нельзя передать прямой ответ
- информация искажается
- контроль частичный

# 3. IN-GAME TRUTH

Игрок сталкивается с:
- повтором 3 дней;
- информационными аномалиями;
- déjà vu в тексте и диалогах;
- несостыковками в сообщениях, предметах, событиях и поведении NPC.

Важно:
игрок может интерпретировать происходящее как "аномалию",
но визуально мир остаётся нормальным.

Фоны, окружение и палитра не показывают поломку реальности.
Аномалия в AVOS_S = информация, событие или интерпретация,
а не визуальный эффект.

# 5. LOOP SYSTEM

## Структура: множественные петли

Игра состоит из пролога (петля 1) и повторяющихся циклов петли 2+.

| Итерация | Роль | Концовки | Переход |
|---|---|---|---|
| 001 | Линейный пролог, онбординг | Одна (автоматическая) | `loop1_to_iter2_reset` → воскресенье |
| 002 | Петля активна, игрок помнит | Любая ложная (NPC / System) | `tue_rooftop_loop_signal` → `loop1_to_iter2_reset` |
| 003+ | Повтор петли, накопление опыта | Любая ложная (NPC / System) | `tue_rooftop_loop_signal` → `loop1_to_iter2_reset` |
| Любая (002+) | — | Истинная (Synthesis) | `-> END` → меню, `game_completed = true` |

Каждая петля:
- 3 дня (воскресенье / понедельник / вторник)
- концовка на крыше
- после ложной концовки — **немедленный перезапуск в воскресенье** (без меню)

### Петля 1 (Итерация 001) — линейный пролог

Петля ещё не запущена с точки зрения игрока:
- одна концовка — автоматический переход в петлю 2
- ложных и истинной концовок НЕТ
- по итогу `iteration_number = 002`, meta-state сохраняется
- в офисе — полностью автоматическая сцена (стандартное решение)

Это онбординг: игрок проходит сюжет один раз без давления петли,
получает базовое представление о персонажах и мире.

### Петли 2+ (начиная с 002) — петля активна

С итерации 002 и далее:
- игрок помнит предыдущие петли (`loop_awareness > 0`)
- доступен выбор стратегии в офисе (fallback / clarify / stop_auto)
- доступны ложные концовки (NPC Path / System Path)
- после **двух уникальных ложных концовок** (`false_endings_count >= 2`) открывается истинная концовка
- в офисе на Monday — ветвление на 3 стратегии
- NPC может узнать о петле, если игрок решает рассказать (`loop2_revealed_to_npc`)
- эпилог только после истинной концовки
- True Ending → `-> END` → меню → `game_completed = true`

Ключевое отличие от пролога:
каждая следующая итерация — не сброс, а накопление.
`loop_awareness`, `false_endings_count`, `iteration_number` растут.
Мир каждый раз воскресный, но восприятие игрока — нет.

# 6. PROGRESSION MODEL

## Петля 1 (пролог)

Линейное прохождение без ветвления концовок.
Автоматический переход в петлю 2 через `loop1_to_iter2_reset`.

## Петли 2+ (финальный блок)

Начиная с петли 2, доступны три пути:

1. **NPC Path** → False Ending 1 — фокус на отношениях, непонимание системы
2. **System Path** → False Ending 2 — логическое решение, без контекста
3. **Synthesis Path** → True Ending → Эпилог → Финал игры

True Ending открывается только после двух уникальных ложных концовок.

Runtime-гейт: `false_endings_count >= 2`.

После True Ending:
- `game_completed = true`
- возврат в меню
- игра считается пройденной

`loop_awareness` — накопленное понимание петли.
Влияет на loop-aware реплики и тон, но не является прямым гейтом True Ending.

# 9. PARAMETERS

TRUST — отношения с NPC → открывает NPC Path

INSIGHT — понимание системы → открывает System Path

SYNC — способность соединить отношения, понимание системы и действие → нужен для True Ending.
*На данный момент инкрементится, но ещё не проверяется в гейтах (будет реализовано позднее).*

Важно:
`ACTION` как отдельный параметр не используется.
В runtime и Ink-гайде канонический третий драм-флаг — `SYNC`.

# 10. ENDINGS SYSTEM

## Петля 1 — линейный финал

Одна концовка — переход в петлю 2. В ink — переход через `loop1_to_iter2_reset`.

## Петли 2+ — три типа концовок

### False 1 (NPC Path)
- фокус на отношениях
- чувство близости
- недостаток понимания системы
- в ink: `# loop:end:false:ending_npc`
- в ink: `~ false_endings_count = false_endings_count + 1`
- эффект: `tue_rooftop_loop_signal` → `loop1_to_iter2_reset` → новое воскресенье
- `iteration_number` инкрементируется
- `loop_awareness` инкрементируется
- `false_endings_count` сохраняется
- journal entry "npc_path"

### False 2 (System Path)
- логическое решение
- недостаток контекста и поведения
- в ink: `# loop:end:false:ending_system`
- в ink: `~ false_endings_count = false_endings_count + 1`
- эффект: `tue_rooftop_loop_signal` → `loop1_to_iter2_reset` → новое воскресенье
- `iteration_number` инкрементируется
- `loop_awareness` инкрементируется
- `false_endings_count` сохраняется
- journal entry "system_path"

### True (Synthesis)
- объединение понимания
- отказ от автоматического решения
- в ink: `# loop:end:true`
- доступна только когда `false_endings_count >= 2`
- эффект: `tue_rooftop_loop_signal` → `-> END` → меню → `game_completed = true`

> Подробнее по runtime-логике концовок и тегам ink — `docs/reference/LOOP_SYSTEM.md`.

# 11. POST-ITERATION SYSTEM

После каждой концовки:

1. **Ложные концовки (NPC / System):**
   - игрок **не возвращается в меню**
   - управление переходит в `tue_rooftop_loop_signal`, который направляет в `loop1_to_iter2_reset`
   - мир сбрасывается в воскресенье
   - `iteration_number` увеличивается на 1 (накопление итераций)
   - `loop_awareness` увеличивается на 1
   - `false_endings_count` не сбрасывается — накапливается между петлями
   - все локальные флаги (предметы, хотспоты, квесты) сбрасываются
   - meta-состояние (journal entries, выбор персонажа) сохраняется

2. **Истинная концовка (Synthesis):**
   - `-> END` — возврат в меню
   - `game_completed = true`
   - игра считается пройденной

3. В journal фиксируется пройденный путь.

---

## Journal entries (только Петли 2+)

После NPC Path:
`meta.add_journal_entry("npc_path")`

После System Path:
`meta.add_journal_entry("system_path")`

После Synthesis:
`meta.add_journal_entry("synthesis")`

Journal entries хранятся в `meta_state` и переживают итерации.
Они не дают инструкций, только фиксируют пройденные пути.

# 12. QUEST / JOURNAL SYSTEM

В AVOS_S есть две разные системы, которые нельзя смешивать:

1. Phone Quests — текущие задачи внутри одной итерации.
2. Loop Journal / Hypothesis Journal — накопленный журнал понимания петли.

---

## Phone Quests

Phone Quests — это задачи в телефоне игрока.

Они:
- живут только внутри текущего прохождения;
- хранятся в runtime `game_state`;
- сбрасываются при старте новой итерации;
- описывают текущие практические цели игрока;
- помогают игроку не потеряться в маршруте.

Примеры:
- найти телефон;
- ответить NPC;
- собраться перед встречей;
- добраться до офиса;
- проверить последствия.

Phone Quests не являются памятью петли.
Они не должны хранить глобальное понимание игрока о прошлых концовках.

---

## Loop Journal / Hypothesis Journal

Loop Journal — это мета-журнал гипотез и осознания.

Он:
- переживает итерации;
- отражает накопленное понимание игрока;
- связан с ложными концовками, повтором и `loop_awareness`;
- не даёт прямых инструкций;
- формулируется как догадки, обрывки памяти и выводы.

Примеры записей:
- "Я лучше понял её. Но этого недостаточно."
- "Я попытался разобраться. Но что-то не сходится."
- "Это связано. Я не должен просто применять это."

Loop Journal не равен обычным phone quests.
Это отдельный слой прогрессии петли.

# 13. ANOMALIES

Аномалии в AVOS_S — не визуальные поломки мира, а данные,
которые игрок и ГГ пытаются интерпретировать.

Они могут быть:
- правдивыми;
- искажёнными;
- неполными;
- противоречивыми.

Типы:
- предметы с информацией;
- SMS;
- письма;
- заметки;
- квестовые формулировки;
- события;
- déjà vu в тексте;
- странные реакции или оговорки NPC.

Игрок может сказать или подумать, что "увидел что-то странное",
но это должно подаваться через текст/диалог/интерпретацию,
а не через фоновые визуальные аномалии.

# 16. KEY IMPLEMENTATION DETAILS

- **Reset flow (ложные концовки):** `tue_rooftop_loop_signal` проверяет `current_iteration_end`. Если `!= "true"` → `-> loop1_to_iter2_reset`. Если `== "true"` → `-> END`.
- **`loop1_to_iter2_reset`:** сбрасывает все игровые флаги (`~ x = false`), предметы (`# remove_item:`), пересобирает телефон. Инкрементирует `iteration_number` и `loop_awareness`. Заканчивается в `apartment_start`.
- **`false_endings_count`:** не сбрасывается в reset. Инкрементируется в каждом ложном финале (`~ false_endings_count = false_endings_count + 1`).
- **Сброс Lua-флагов:** `# set_flag:...=false` для всех критических флагов хотспотов (`park_npc_at_bench`, `kitchen_morning_seen`, `monday_folder_taken` и др.) и квестовых флагов (`mon_office_error_seen`, `reached_office` и др.).
- **Office-ветвление:** при `iteration_number <= 1` — автоматическое стандартное решение. При `iteration_number >= 2` — выбор из 3 стратегий.
