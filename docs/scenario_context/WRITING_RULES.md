# Writing Rules For GPT

Эти правила нужны для GPT, который помогает писать Ink, хабы и хотспоты.

## Главный принцип

Не изобретай новый рантайм. Используй только те механики, которые уже есть в проекте, или явно помечай, что предлагаешь новую механику, которую нужно реализовать в коде.

## Версионирование (правило перед всеми остальными)

Канон — **только файлы, приложенные в текущей сессии**, и актуальный
`PROJECT_INVENTORY.md` из этой же сессии. В ChatGPT текущие source-файлы обычно
лежат как `/mnt/data/<file>`. Если file search / project knowledge поднимает
одноимённый файл из прошлых чатов — он почти всегда устарел, **игнорируй**,
особенно если структура расходится с приложенным сейчас.

Нельзя смешивать chunks разных эпох. Если `/mnt/data/shop.lua` использует
`s.nav_scene{}`, `s.inspect{}`, `s.pickup{}` и scene_id `shop_street`,
`shop_front`, `shop_household`, то найденный через поиск старый `shop.lua` с
`hotspot_style`, прямым `action = {...}`, `bg_shop_day`, `arrow_up` или
битой Lua-конкатенацией не является контекстом. Это архивный мусор для текущей
задачи.

Приоритет источников: текущий `/mnt/data/<file>` → явно приложенный source-файл
текущей сессии → `PROJECT_INVENTORY.md` текущей сессии → спросить пользователя.
См. `README.md` секцию «Версионирование контекста».


## Гигиена файлов AI-выводов

Это продолжение правила версионирования. Корень `/mnt/data` должен оставаться чистым: там лежат только файлы, загруженные пользователем в текущий контекст, и актуальные source/documentation файлы проекта.

AI не должен создавать свои черновики, исправленные версии и отчёты прямо в корне `/mnt/data`. Любой файл, созданный AI, складывать только в отдельную папку:

```text
/mnt/data/ai_outputs/
```

Для каждой задачи создавать отдельную подпапку с коротким slug'ом:

```text
/mnt/data/ai_outputs/<task_slug>/
```

Внутри задачи использовать структуру:

```text
/mnt/data/ai_outputs/<task_slug>/ready/    -- финальные файлы, которые можно переносить в проект
/mnt/data/ai_outputs/<task_slug>/drafts/   -- промежуточные версии, эксперименты, временные файлы
/mnt/data/ai_outputs/<task_slug>/reports/  -- аудиты, списки проблем, проверки связей
/mnt/data/ai_outputs/<task_slug>/patches/  -- diff/patch, если нужны
```

Примеры:

```text
/mnt/data/ai_outputs/cafe_sunday_rework/ready/cafe.lua
/mnt/data/ai_outputs/cafe_sunday_rework/ready/cafe_sunday.ink
/mnt/data/ai_outputs/viewpoint_sunday_rework/reports/check_result.md
```

Запрещено создавать в корне `/mnt/data` файлы вида:

```text
cafe_full.lua
cafe_sunday_fixed.ink
shop_sunday_no_early_home.ink
viewpoint_sunday_route_aware.ink
*_full.*
*_fixed.*
*_polish.*
*_route_aware.*
*_no_early_home.*
```

Если нужен финальный файл с тем же именем, что и source-файл проекта, он всё равно должен лежать в `ready/` внутри задачи, например:

```text
/mnt/data/ai_outputs/viewpoint_sunday_rework/ready/viewpoint_sunday.ink
```

Файлы из `ai_outputs` не являются каноном сами по себе. Каноном они становятся только после того, как пользователь перенёс их в проект, обновил реальные source-файлы, прогнал нужные проверки / `generate_scenario_inventory.py`, и заново загрузил свежие файлы в текущий контекст.

Перед ответом с готовыми файлами AI должен давать ссылки именно на файлы из `ready/`, а не на черновики из `drafts/`. Если задача была только аудитом, итоговый отчёт класть в `reports/`.

## Жёсткое правило для ChatGPT / file_search

Результаты file_search по source-файлам (`*.ink`, `*.lua`,
`PROJECT_INVENTORY.md`, `LOCATIONS_GUIDE.md`, `TEMPLATES.md` и т.п.) считать
**недоверенными**, если файл не приложен в текущей сессии и не доступен как
текущий `/mnt/data/<file>`.

Если file_search находит одноимённый файл, но пользователь не загружал его в
текущий контекст, **не использовать его как источник правки**. Его можно только
упомянуть как потенциально устаревший результат поиска.

Канон:

1. Файлы, загруженные пользователем в текущий контекст.
2. Текущий `/mnt/data/<file>`, если файл реально доступен.
3. Актуальный `PROJECT_INVENTORY.md`, загруженный в текущий контекст.
4. Если нужного source-файла нет — запросить его у пользователя.

Запрещено:

- править `.ink` или `.lua` по найденным file_search chunks;
- смешивать текущие документы с найденными старыми source-файлами;
- цитировать старый файл как актуальный, если пользователь не загружал его сейчас.

Если пользователь загрузил `shop.lua` — читать именно его. Если не загрузил —
не делать вид, что старый `shop.lua` из поиска актуален.

## Ink-правила

- Сохраняй существующие knot names, если нет отдельной задачи на переименование.
- Не создавай переход `-> some_knot`, если не пишешь сам `=== some_knot ===` или не уверен, что он уже есть.
- Карта живёт только в телефоне (`# phone:map`). Standalone map / `# map:hub:KNOT` удалены — не использовать.
- Если задача использует теги, сверяйся с `INK_TAG_REFERENCE.md`. `dialogue_manager_ink.lua` нужен только для изменения или отладки самих тегов.
- Теги пиши отдельными строками рядом с тем местом, где они должны сработать.
- Не добавляй флаги без понятного назначения.
- Не делай важные последствия только текстом. Если выбор должен влиять на игру, нужен флаг/переменная/тег.
- Не ломай `94_phone_mail.ink`: это заготовка под почту, её нельзя считать мусором.

## Когда обязательно запрашивать source-файлы

Если в `PROJECT_INVENTORY.md` нет информации для уверенного ответа — **сначала запроси нужный файл, не догадывайся**. Конкретные триггеры:

- **Добавляешь новый VAR / трогаешь падежные формы / меняешь стартовое состояние** → запроси `00_bootstrap.ink`. Не выдумывай `VAR` или формы — список существующих в bootstrap'е, и они могут уже быть.
- **Меняешь логику выбора персонажа / mc_gender / mc_name** → `00_bootstrap.ink` + `10_apartment.ink` (там реальная инициализация при `choose_character`).
- **Правишь существующий хотспот (нужны точные `rect`, `id`, `visible_when`)** → запроси `main/data/scenes/<location>.lua`.
- **Используешь конкретный `STYLE_*` / иконку / bg-helper** → `_shared.lua`.
- **Подозрение, что нужный knot существует, но имя не помнишь** → `PROJECT_INVENTORY.md` (раздел Knots) + потом сам ink-файл.
- **Проверяешь поддерживается ли ink-тег** → `INK_TAG_REFERENCE.md`, а не угадывать.

Если запрашиваешь файл — называй его точно (полный путь). Не «дай мне bootstrap» — а «дай `main/story/chapters/00_bootstrap.ink`».

## Выборы

Выборы должны иметь последствия, но лог диалога не должен позволять их откатывать.

Если игрок уже:

- выбрал маршрут;
- ответил в важной реплике;
- получил предмет;
- потратил предмет;
- изменил доступность карты;
- завершил сцену;

то это нельзя превращать в простой "откат назад". Лог нужен для чтения, не для отмены истории.

## Телефон и карта

Карта = phone-приложение. Из Ink её открывает `# phone:map`. Standalone-карта удалена.

Если нужно временно ограничить карту, используй смысловые операции:

- разрешить точку;
- заблокировать точку;
- заблокировать все точки;
- оставить только одну точку;
- сбросить ограничения.

Точные имена `poi_id` надо брать из текущих файлов телефона/карты.

## Хотспоты

Обычные хотспоты описываются в `main/data/scenes/*.lua`, а не руками в GUI.

GPT может предлагать готовый Lua-блок, но должен учитывать:

- координаты в 1280x720;
- `id` уникальный внутри сцены;
- `label` короткий и понятный;
- `action` использует поддерживаемый тип;
- `visible_when` только скрывает/показывает;
- `condition` блокирует действие, но может оставить хотспот видимым;
- `style` отвечает за внешний вид круга/иконки;
- `icon_offset` можно использовать, если иконка из шрифта визуально смещена.

## Стиль текста

- Пиши живой диалог, не объяснение лора.
- Давай конкретные детали локации.
- Не делай персонажей одинаковыми по голосу.
- Не перегружай сцену техническими словами.
- Не раскрывай тайну раньше времени.
- Помни, что игрок может проходить сцену на телефоне короткими сессиями.

## Gender tokens (согласование глаголов по полу MC)

Синтаксис строгий: `<корень>{mc_gender == "female":<окончание_female>|<окончание_male>}`.

**Почему female первой:** это базовая семантика ink. В `{условие: A | B}` ветка A берётся когда условие = true, B — когда false. Наше условие — `mc_gender == "female"`. Значит true = female = первая ветка (до пайпа). Запомнил один раз — больше не путаешь.

**Алгоритм написания:**
1. Выпиши обе формы целиком: female=«приняла», male=«принял».
2. Найди общий корень (одинаковые буквы с начала): «принял».
3. Окончания: female=«а», male=«» (пусто).
4. Собери: `принял{mc_gender == "female":а|}` (female-окончание ДО пайпа, male — ПОСЛЕ).

Типовые правильные формы:

```ink
сел{mc_gender == "female":а|}        // female: села, male: сел
взял{mc_gender == "female":а|}        // female: взяла, male: взял
принял{mc_gender == "female":а|}      // female: приняла, male: принял
долж{mc_gender == "female":на|ен}     // female: должна, male: должен
приш{mc_gender == "female":ла|ёл}     // female: пришла, male: пришёл
```

**Главная ошибка AI — инверсия** (female-окончание оказалось в male-ветке):

```ink
принял{mc_gender == "female":|а}      ✗  female: «принял» (мужская!), male: «приняла» (женская!) — наоборот, плюс некоторые версии ink дают parse-error на пустую первую ветку
```

Если поймал инверсию — **просто поменяй местами куски до и после пайпа**: было `:|а` → стало `:а|`. Корень и условие трогать не надо.

**Самопроверка:** мысленно подставь female → возьми ветку ДО пайпа → склей с корнем → должна выйти **женская** форма. Если вышла мужская — инверсия, разверни.

Полная таблица типовых форм и других ошибок — `NARRATIVE_STATE.md` секция **Gender tokens**. Условие всегда `mc_gender == "female"`, никаких `mc_gender == "male"` для инверсии.

## Склонение имён

Не подставляй `{mc_name}` и `{npc_name}` механически во все фразы. Эти переменные находятся в именительном падеже.

Если по-русски требуется другой падеж, используй готовые Ink-переменные:

- родительный: `{mc_name_gen}`, `{npc_name_gen}`
- дательный: `{mc_name_dat}`, `{npc_name_dat}`
- винительный: `{mc_name_acc}`, `{npc_name_acc}`
- творительный: `{mc_name_ins}`, `{npc_name_ins}`
- предложный: `{mc_name_prep}`, `{npc_name_prep}`

Примеры:

- `{npc_name_gen} нигде не видно.`
- `Можно написать {npc_name_dat}.`
- `Ты идёшь рядом с {npc_name_ins}.`
- `Говорить о {npc_name_prep} сейчас странно.`

Если фраза начинает звучать искусственно из-за подстановки имени, лучше переписать её без имени. Например, заменить `сообщение от {npc_name_gen}` на `сообщение в Messenger`, если имя уже понятно из контекста.

## Формат ответа от GPT

Лучший формат ответа:

- короткое описание, что меняется;
- готовый Ink или Lua-фрагмент;
- список новых/использованных флагов;
- список мест, куда это надо вставить;
- риски, если они есть.
