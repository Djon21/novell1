# Narrative State

Что важно понимать про state-систему проекта при написании сцен. Этот
документ — концептуальный. Реальный список существующих флагов / items —

## Где живёт состояние

| Слой | Где | Что хранит |
|---|---|---|
| **Ink VAR** | `~ var_name = ...` в .ink файлах | Сценарные переменные, отношения, счётчики, выбранные варианты, gender/name |
| **Game state flags** | `gs.set_flag(...)` / `# set_flag:NAME=...` | Боевые флаги рантайма — читают сцены, хотспоты, телефон, инвентарь, scene_characters |
| **Inventory** | `gs.add_item(...)` / `# add_item:ID` | Предметы игрока |
| **Phone state** | `gs.add_sms/msg/mail/note/call/clue/...` | SMS, Messenger-чаты, mail, заметки, журнал звонков, улики, terminal |
| **Phone pin-теги** | `# sms:tag` / `# sms:need_reply` / `# msg:tag` / `# msg:need_reply` | Цветные пин-плашки на чатах в списке (визуальный маркер «срочное / ждёт ответа»). Авто-снимаются при `reply`. Сериализуются в save. |
| **Phone prompts** | `# msg:prompt:CHAT:KNOT[:LABEL]` | «Открытая инициатива в чате»: разрешает писать в чат игнорируя `msg_<chat>_replied` и при тапе input'а диверитит в указанный KNOT (вместо `msg_thread_<chat>`). Заменяет хотспоты «Написать». Авто-снимается при `# msg:reply:CHAT:...` внутри knot'а. |
| **Map state** | `gs.map_allow/lock_to/lock_all` | Доступность POI на карте |
| **Meta state** | `meta.inc/set` | Cross-loop счётчики, awareness, false_endings_seen |

Если AI пишет **только текст реплик** — обычно достаточно ink VAR + тегов. Если пишет **хаб с условиями** — нужны game flags + scene Lua. Если хочет дать игроку возможность **написать первым** в чат NPC из конкретной сцены — `# msg:prompt`, не хотспот.

## Gender tokens

Для согласования глаголов с полом MC есть синтаксис:

```ink
Я почти не успел{mc_gender == "female":а|} начать волноваться.
```

- `mc_gender` — `"male"` или `"female"`, инициализируется в `choose_character`
- Условие в ink: `{mc_gender == "female": ...текст для женского...|...для мужского...}`

### Ментальная модель — почему female ПЕРВОЙ

Это не наша конвенция, а базовая семантика ink-условия:

```
{ <условие> : <ветка-true> | <ветка-false> }
                   ▲              ▲
              когда условие  когда условие
                  true           false
```

Наше условие — `mc_gender == "female"`. Значит **первая ветка (до пайпа) = female**, **вторая (после пайпа) = male**. Это просто. Если запомнишь так — никогда не перепутаешь порядок.

### Алгоритм «как написать»

Допустим, нужно «приняла / принял»:

1. **Выпиши обе формы:** female=«приняла», male=«принял».
2. **Найди общий корень** (одинаковая часть с начала): «принял».
3. **Окончания после корня:** female-окончание = «а», male-окончание = «» (пусто).
4. **Собери шаблон:** `корень{mc_gender == "female":female-оконч|male-оконч}` → `принял{mc_gender == "female":а|}`.

Если бы было «должна / должен»: корень «долж», female=«на», male=«ен» → `долж{mc_gender == "female":на|ен}`.

**Если female-окончание пустое, а male не пустое — корень выбран неправильно.** Сдвинь корень короче, чтобы female-окончание было непустым. Пример: для «приняла / принял» корень «приня» даст female=«ла», male=«л» (тоже валидно). Корень «принял» даст female=«а», male=«» (тоже валидно). Корень «принял» с female=«» и male=«а» ✗ — это инверсия (см. ниже).

### Типовые правильные формы

| Female / Male | Шаблон |
|---|---|
| села / сел | `сел{mc_gender == "female":а\|}` |
| взяла / взял | `взял{mc_gender == "female":а\|}` |
| хотела / хотел | `хотел{mc_gender == "female":а\|}` |
| сделала бы / сделал бы | `сделал{mc_gender == "female":а\|} бы` |
| должна / должен | `долж{mc_gender == "female":на\|ен}` |
| одна / один | `од{mc_gender == "female":на\|ин}` |
| пришла / пришёл | `приш{mc_gender == "female":ла\|ёл}` |
| вернулась / вернулся | `вернул{mc_gender == "female":ась\|ся}` |
| увидела / увидел | `увидел{mc_gender == "female":а\|}` |

**Принцип выбора корня:** обрезаем слово до буквы, где male и female расходятся. Если male форма «сел» и female «села» — общий корень `сел`, добавляется только «а». Если male «пришёл» и female «пришла» — общий корень `приш`, оба окончания разные (`ёл` / `ла`). Никогда не пиши `пришёл{...:ла|}` — получится «пришёлла» для female.

### Частые ошибки AI-сценариста (НЕ ДЕЛАТЬ)

| ✗ Неверно | Что не так | ✓ Как надо |
|---|---|---|
| `сел{mc_gender == "female":\|а}` | **Инверсия:** female-ветка пуста, female-окончание «а» по ошибке оказалось в male-ветке. Результат для female MC = «сел» (мужская форма!), для male MC = «села». Плюс некоторые версии ink дают parse-error на пустую ветку. | `сел{mc_gender == "female":а\|}` (female=«а» ДО пайпа, male=пусто ПОСЛЕ) |
| `{mc_gender == "female":села\|сел}` (без корня) | Работает, но многословно и шумно для глаза. | `сел{mc_gender == "female":а\|}` (только окончания после общего корня) |
| `сел{mc_gender == "female":а}` (без пайпа) | Male-ветки нет вообще → ink интерпретирует как fallback и male получит пустоту. | `сел{mc_gender == "female":а\|}` (пайп ставить ВСЕГДА) |
| `сел{mc_gender == "male":\|а}` (инверсия условия) | Технически работает, но условие читается наоборот. Следующий читатель/AI запутается. | условие всегда `mc_gender == "female"` |
| `сел{a}` или `сел{а\|}` (забыл условие) | Без `mc_gender == ...:` ink не знает на что условие — parse-error. | весь блок целиком `{mc_gender == "female":а\|}` |
| `принял{mc_gender == "female":\|а}` для «приняла/принял» (реальный кейс) | То же что строка 1 — инверсия. Female-окончание `а` должно стоять ДО пайпа. | `принял{mc_gender == "female":а\|}` |

**Самопроверка перед отправкой реплики:** мысленно подставь female вместо `mc_gender == "female"` (т.е. условие = true) → возьми **ПЕРВУЮ** ветку до пайпа → склей корень + первую ветку → должна получиться **женская** форма. Если получилась мужская — у тебя инверсия, поменяй ветки местами.

**Главное правило:** условие всегда `mc_gender == "female"`, female-вариант ПЕРВЫЙ (до пайпа), male-вариант ВТОРОЙ (после пайпа, может быть пустой строкой). Никаких инверсий.

Также есть VAR `npc_gender` (зеркало). Используй когда нужно согласовать речь NPC по полу его персонажа. Тот же синтаксис: `{npc_gender == "female":а\|}`.

## Сюжетные параметры (концепции)

В Ink можно встретить такие сюжетные характеристики:

- **Выбранный персонаж** (`mc_gender` + `mc_name`)
- **День истории** (sunday / monday / tuesday) — обычно отслеживается через флаги вида `sunday_finished`, `monday_*`, `tuesday_*`
- **TRUST** — уровень доверия NPC (увеличивается за внимательные диалог-выборы)
- **INSIGHT** — уровень наблюдательности / понимания происходящего
- **SYNC** — синхронизация с NPC / близость к петле

Точные имена variables / счётчиков смотри в текущем ink-файле перед добавлением новых. **Не создавай новые VAR если есть похожие**.

## Карта и Phone POIs

Карта — это часть телефона (не отдельный экран).

Управление картой из ink:
- `# map:allow:poi_id` — разрешить точку
- `# map:lock_to:poi_id` — оставить доступной только эту точку
- `# map:lock_all` — заблокировать все
- `# map:allow:reset` — снять временные ограничения

Список существующих `poi_*` — в `PROJECT_INVENTORY.md` секция **Phone Map POIs**.

## Лог диалога (backlog)

В игре есть read-only лог реплик (HUD-кнопка LOG). Игрок может **перечитать**, но **не должен откатывать** выборы / предметы / переходы / флаги.

Реализация: `main/scripts/dialogue_backlog.lua`. Записи добавляются при render каждой реплики, хранится в circular buffer.

## Cross-loop meta state

Часть состояния сохраняется **между итерациями** (петлями) для постепенного раскрытия мира:
- `iteration_number` — номер итерации
- `iteration_label` — форматированная (например `001`)
- `loop_awareness` — растёт со сценами осознания петли
- `false_endings_seen` — set ложных концовок которые игрок уже видел

Управление: `# meta:add:KEY:N` (для числовых), `# meta:set:KEY:VALUE`.

Эти переменные **не сбрасываются при переходе в следующую петлю** (`chapter_finished` / `loop:end:true` -> `meta.complete_iteration()`).

Важно про терминологию: runtime-сообщение `reset_iteration` сейчас используется как **полный ручной сброс прогресса петли из меню**. Оно вызывает `meta.reset_all()` и возвращает проект к состоянию новой игры. Не путать его с сюжетным переходом Iter 1 -> Iter 2.


### Iter 2: повтор мира и новое состояние героя

При переходе из iter 1 в iter 2 мир должен вернуться в воскресенье, но cross-loop meta state остаётся. Это значит:

- бытовые/day-флаги воскресенья, понедельника и вторника можно сбрасывать как состояние мира;
- `iteration_number`, `loop_awareness`, `false_endings_seen` и другие meta-ключи не сбрасываются;
- герой в тексте может помнить/ощущать предыдущую последовательность событий сильнее, чем мир вокруг;
- NPC и сервисные системы в начале воскресенья ведут себя как в первом воскресенье, пока герой не отвечает/действует иначе.

Канон ветвления: **одинаковый внешний стимул → новый ответ героя → новая реакция мира**. Первое сообщение NPC во втором воскресенье должно повторять первое воскресное сообщение из iter 1 дословно. После другого ответа героя NPC реагирует уже на этот новый ответ, не на прошлую итерацию.

Не использовать для этого отдельные «сломанные» варианты даты как новый глобальный день. Субъективная `wednesday`-обманка — это presentation/narrative layer. Фактический state после reset — воскресенье новой итерации.

### Телефон при входе в новую петлю

Для Iter 2 нужен отдельный runtime-механизм пересборки телефона под новое воскресенье, условно `# phone:loop_reset`.

Контракт такого тега должен быть узким:

- очистить runtime SMS/Messenger/phone prompts/tags/unread старой итерации;
- откатить bank runtime: баланс возвращается к стартовому воскресному значению, банковские SMS потом заново добавляются seed-событиями;
- не трогать cross-loop meta state (`iteration_number`, `loop_awareness`, `completed_iterations`);
- не сбрасывать выбор персонажа;
- после очистки сценарий заново вызывает seed-события телефона (`-> phone_sms_seed_sunday_morning ->`, `-> phone_msg_seed_sunday_morning ->`) и новые Iter 2 телефонные события;
- не использовать обычный `reset_iteration` для этой задачи, потому что он сейчас означает полный сброс meta-прогресса.

`phone:loop_reset` уже поддержан runtime. Используй его только в точке входа новой петли, до повторного seed телефона. Не ставь его внутри обычных сцен воскресенья, иначе игрок потеряет текущие переписки и баланс.
